# Tiered sensitivity findings Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** After every TMI scan, the primary output is a harm-ordered list of findings (H1–H6) each carrying harm, confidence, and subject — while the legacy 11-category exposure score remains as a corpus-volume readout.

**Architecture:** Keep `lib/pipeline/` and the 11-category aggregator untouched in their counting behavior. Add a scanner-only projection: promote existing category hits into findings, run a small pure-function detector pass for the gaps (secrets, health, profile URLs, gov/payment IDs, precise location), classify subject with cue windows, and attach `findings`, `bands`, `readouts`, and `coverage` onto the report dict `scan()` already returns. The browser port copies those pure functions into `web/lib/` and must match Python fixtures. No LLM.

**Tech Stack:** Python scanner (`lib/scanner/`, `api/scanner.py`, `phonenumbers==8.13.27`), browser TMI (`web/lib/*`, `web/worker.js`, vendored `libphonenumber-js` 1.10.53), local UI (`public/scanner/`), fixture scripts (`scripts/web_fixtures_*.py`), Node built-in test runner (`tests/web/*.test.mjs`), pytest (`tests/`).

## Global Constraints

- Roots that exist and must be used: `lib/scanner/`, `web/lib/`, `public/scanner/`, `tests/`, `tests/web/`. Do not invent a parallel `src/` tree.
- Browser TMI must reproduce Python on shared fixtures (`tests/web/scan.test.mjs` deep-equals `tests/web/fixtures/stage1.json`, regenerated by `scripts/web_fixtures_scan.py`). Extract shape is a separate fixture (`tests/web/fixtures/extract.json` via `scripts/web_fixtures_extract.py`). Do not change the serialized `Extracted` fields in the same change as detector work.
- Real values never leave the report. Examples and findings store masked text only. `RedactionToken.original` stays server-side and is already stripped on serialize (`lib/types.py`).
- Do not add token types to `TokenType` in `lib/types.py`. Do not run new detectors inside `lib/pipeline/index.py`. Private chat / anonymizer is out of scope.
- English UI and English lexicon only, plus the few German immigration phrases already in `scripts/compute_sensitivity_axes.py` (`aufenthaltstitel`, `blue card`). No general multilingual expansion.
- 5,000,000 character cap stays (`MAX_SCAN_CHARS` in `lib/scanner/scan.py` and `web/lib/scan.js`). Assistant messages stay skipped. `user.json` stays out of chat segments (`ACCOUNT_FILE_RE` in `lib/scanner/extract.py` and `web/lib/extract.js`).
- Code fences stay blanked for the PII pipeline (`CODE_BLOCK_RE`). Secrets are the only extra pass allowed inside fences.
- Legacy keys stay: `source`, `totals`, `score`, `level`, `categories` (the 11 keys, `tier` still `"direct"` | `"context"`). `exposure_score()` math stays (`DIRECT_POINTS = 4`, `CONTEXT_POINTS = 1`, `SCORE_SCALE = 40`).
- LLM is not required for any task in this plan. The optional detective model stays what it is: PERSON / ORG / LOCATION only (`web/lib/detective.js`).
- Non-goals: fixing “You’re 29” age grammar, ISO travel dates, school-name NER, PNR+surname combo, scanning assistant messages, raising the character cap, a fourth 0–100 headline.

## 1. Goal and architecture

TMI today answers “how much biography is in this export?” `lib/scanner/scan.py` chunks user text (fences blanked, 5M cap), runs the anonymizer pipeline, and `lib/scanner/report.py` `Aggregator` rolls tokens into 11 categories. `exposure_score()` saturates on unique names, places, and dates, so a live AWS key and a health disclosure look the same as a noisy name bag: a high corpus score. The prototype in `lib/scanner/sensitivity_axes.py` papers over that with a second regex pass and four meters, but it never emits per-span findings, it is not on the scan path, and the browser does not implement it.

The replacement is a projection, not a new pipeline. `scan()` keeps building the legacy report so `tests/test_mock_memories.py`, `tests/test_scanner.py`, and the category counts in `tests/web/fixtures/stage1.json` stay meaningful. On the same prepared text it builds **findings**: each one is a masked span plus three axes (harm H1–H6, confidence, subject). Existing categories are *promoted* through the mapping in section 5 so phones and dates are not detected a second time. New detectors fill holes the 11 categories cannot represent (secrets, health, profile URLs, checksummed government IDs, precise location). Findings are sorted by harm, then confidence, then subject. That ordered list is what the mirror and both UIs lead with. Three 0–100 readouts (credentials, intimate/safety, identity bridges) are summaries of H1, H3, and account-holder H4. `score` / `level` remain, relabeled in the UI as corpus volume. Coverage (truncation, skipped `user.json`, binaries, blanked fences, skipped assistant messages) is a footnote that marks every readout as a lower bound. It is not a seventh harm band and it does not subtract points.

Roll out in three phases that each leave the product runnable. Phase 1 lands the Python report fields and detectors behind the existing API with no headline change. Phase 2 ports the pure functions to `web/lib/` and regenerates fixtures so `node --test tests/web/scan.test.mjs` stays the parity gate. Phase 3 points the mirror, `public/scanner/app.js`, and `web/app.js` at findings. `web/worker.js` already posts `report` through; it needs no scoring logic if `web/lib/scan.js` attaches the new keys.

## 2. Report schema v2

Additive. `schemaVersion: 2` means the new keys are present. Absence of the key means a legacy consumer. Do not renumber or remove category objects.

### Top-level shape

```json
{
  "schemaVersion": 2,
  "source": {
    "format": "chatgpt_export",
    "label": "ChatGPT export",
    "conversations": 6,
    "piecesScanned": 11,
    "piecesWithFinds": 4,
    "kinds": {"profile": 2, "message": 9},
    "assistantMessagesSkipped": 7,
    "codeBlocksSkipped": 1,
    "charactersScanned": 12000,
    "charactersSkipped": 0,
    "truncated": false,
    "failedChunks": 0
  },
  "totals": {"mentions": 20, "unique": 16, "directUnique": 8, "contextUnique": 8},
  "score": 66,
  "level": "oversharer",
  "categories": [
    {
      "key": "emails",
      "label": "Email addresses",
      "tier": "direct",
      "count": 1,
      "unique": 1,
      "examples": [{"masked": "p••••@e••••••.com", "count": 1}]
    }
  ],
  "findings": [],
  "bands": {},
  "readouts": {},
  "coverage": {},
  "elapsedMs": 40
}
```

`charactersSkipped` is new inside `source` and is safe for old clients to ignore. It is the sum of prepared segment lengths minus `charactersScanned` (the budget `scan()` already walks). Do not guess unread bytes inside zip members that were never decoded.

### One finding

```json
{
  "id": "f-03",
  "harm": "H1",
  "kind": "aws_access_key",
  "label": "AWS access key",
  "confidence": "high",
  "subject": "account_holder",
  "masked": "AKIA••••••••••••",
  "category": null,
  "source": "detector",
  "inCodeBlock": false,
  "count": 1
}
```

| Field | Rule |
|---|---|
| `id` | `f-` plus a zero-padded index **after** sort. Not derived from the raw value. |
| `harm` | `H1` … `H6` only. |
| `kind` | Stable snake case from the tables below. UI groups on this. |
| `label` | Short English noun phrase. No raw value. |
| `confidence` | `confirmed` · `high` · `medium` · `low`. `unscanned` is **not** a finding confidence. It lives only on coverage. |
| `subject` | `account_holder` · `third_party` · `unknown` · `not_applicable`. |
| `masked` | Screenshot-safe. Reuse `mask()` in `lib/scanner/report.py` / `web/lib/report.js` when `category` is set. New kinds use the mask profile in section 5. |
| `category` | Legacy key (`emails`, `phones`, …) when the finding was promoted from the aggregator. `null` for detector-only kinds. |
| `source` | `promoted` (from a category hit), `detector` (new pass), or `envelope` (`user.json` contacts). |
| `inCodeBlock` | True only for the fence secret pass. |
| `count` | Mentions of the same normalized value inside this scan. Unique identity is the finding row. |

No `start`, no `original`, no hash of the value. Hashes of emails are still identifiers.

### Bands (full counts, even when `findings` is capped)

```json
{
  "H1": {"unique": 1, "byConfidence": {"high": 1}, "bySubject": {"account_holder": 1}},
  "H2": {"unique": 2, "byConfidence": {"confirmed": 1, "medium": 1}, "bySubject": {"account_holder": 2}},
  "H3": {"unique": 1, "byConfidence": {"low": 1}, "bySubject": {"account_holder": 1}},
  "H4": {"unique": 3, "byConfidence": {"high": 1, "medium": 2}, "bySubject": {"account_holder": 2, "third_party": 1}},
  "H5": {"unique": 0, "byConfidence": {}, "bySubject": {}},
  "H6": {"unique": 40, "byConfidence": {"low": 40}, "bySubject": {"unknown": 30, "third_party": 10}}
}
```

`bands` count **unique findings before the emit cap**. The `findings` array emits at most **12 rows per harm band**, preferring higher confidence, then `account_holder`, then `unknown`, then `third_party`. The UI says “showing 12 of N” using `bands[harm].unique`. H6 still caps at 12 so a name bag cannot bloat the JSON the API returns. Third-party rows are included in that cap; they are not dropped.

### Readouts

```json
{
  "credentials": {
    "harmBand": "H1",
    "score": 80,
    "confidence": "high",
    "lowerBound": true,
    "drivers": {"private_key": 0, "aws_access_key": 1, "api_token": 0, "jwt": 0, "password_cue": 0, "tokenized_url": 0}
  },
  "intimateSafety": {
    "harmBand": "H3",
    "score": 18,
    "confidence": "low",
    "lowerBound": true,
    "note": "Keyword and pattern hits. Not a diagnosis.",
    "drivers": {"health": 1, "religion": 0, "sexual_orientation": 0, "children": 0, "precise_location": 0, "immigration": 0}
  },
  "identityBridges": {
    "harmBand": "H4",
    "score": 42,
    "confidence": "medium",
    "lowerBound": true,
    "aboutYou": 2,
    "aboutOthers": 1,
    "note": "Account-holder bridges only. Name-bag and unvalidated phones are corpus volume."
  },
  "corpusVolume": {
    "harmBand": "H6",
    "score": 66,
    "confidence": "low",
    "lowerBound": true,
    "legacyLevel": "oversharer"
  }
}
```

`readouts.*.score` is 0–100. `readouts.corpusVolume.score` **equals** top-level `score`. Headline confidence is the best confidence among findings that fed that readout (`confirmed` > `high` > `medium` > `low`). If nothing fed it, confidence is `low` and score is 0.

### Coverage

```json
{
  "truncated": false,
  "charactersScanned": 12000,
  "charactersSkipped": 0,
  "truncationNote": null,
  "codeBlocksSkipped": 1,
  "assistantMessagesSkipped": 7,
  "userJsonPresent": true,
  "userJsonSkipped": true,
  "binaryAttachments": 2,
  "unreadMembers": ["ads.json"],
  "lowerBound": true
}
```

`lowerBound` is true when any of these hold: `truncated`, `charactersSkipped > 0`, `codeBlocksSkipped > 0`, `assistantMessagesSkipped > 0`, `binaryAttachments > 0`, `userJsonPresent && userJsonSkipped`, or `unreadMembers` is non-empty. Pasted text with no zip sets `userJsonPresent` / `userJsonSkipped` / `binaryAttachments` to `null` and `unreadMembers` to `[]` (unknown envelope, not “clean”). Copy for the footnote, when `lowerBound` is true: “These findings are a lower bound. Some of the export was not read.” When `truncated` is true, append the existing sentence: “Scanner stopped at 5M characters.”

`unreadMembers` is a denylist of **names only**, capped at 20 strings, matching `(^|/)(ads|summaries|asset_index).*\.json$` and similar index files that `_from_zip` does not put in `wanted`. Do not read their contents.

### Sort order (the product order)

1. Harm: H1, H2, H3, H4, H5, H6.
2. Confidence: confirmed, high, medium, low.
3. Subject: account_holder, unknown, third_party, not_applicable.
4. `kind` alphabetical, then `id` for stability.

Mirror and both apps render `findings` in this order and visually group “About you” (`account_holder`, plus H1 `unknown` secrets the user pasted) vs “About others” (`third_party`). `unknown` non-secrets sit in a collapsed “Not sure who” group. They do not enter the “about you” sentence.

## 3. Phased rollout

### Phase 1 — MVP (Python report, no headline change)

**Done when:** `scan()` on every current entry point returns schema v2; legacy category counts and `score` for `samples/mock-memories/` match today’s tests; new unit tests cover detectors; `POST /api/scan` returns the extra keys; `public/scanner/app.js` and `web/app.js` are unchanged and simply ignore unknown keys.

Deliverables:

- `lib/scanner/findings.py` — sort, cap, bands, promotion, subject, readout math.
- `lib/scanner/detectors.py` — pure functions, no I/O.
- `lib/scanner/envelope.py` — zip namelist + masked `user.json` contacts. Does not alter `Extracted`.
- `lib/scanner/scan.py` wires them.
- `lib/scanner/jobs.py` passes envelope into `scan()`.
- `lib/scanner/sensitivity_axes.py` becomes a thin wrapper over finding readouts so `scripts/compute_sensitivity_axes.py` stops being a second detector implementation.
- Tests listed in section 7. No fixture regen for `stage1.json` yet, because JS `scan()` does not emit the keys yet.

### Phase 2 — Browser parity

**Done when:** `node --test tests/web/detectors.test.mjs tests/web/scan.test.mjs` passes against freshly generated fixtures, and a frisk vs detective scan of the same string yields **identical H1–H3 detector findings** (names may differ).

Deliverables:

- `web/lib/detectors.js`, `web/lib/sensitivity.js`, `web/lib/envelope.js`.
- `web/lib/scan.js` attaches the same keys, using the same prepared text `prepareTexts()` already builds.
- `web/worker.js` calls `readEnvelope` once next to `extractFile` and passes the result into `scan`. No UI change.
- Regenerate `tests/web/fixtures/stage1.json` and add `tests/web/fixtures/detectors.json` in the same change as the JS. Review the JSON diff; do not treat a surprise category-count change as acceptable.

### Phase 3 — Mirror, then both UIs

**Done when:** the mirror leads with H1–H3 masked findings split into about-you / about-others; the three readouts plus corpus volume and the coverage footnote are visible; the legacy meter is visually secondary; a manual pass on one real ChatGPT export (not committed) shows no raw secrets or health words in the DOM.

Deliverables:

- `scripts/build_mirror_mock.py` reads `findings` / `readouts` / `coverage` from `public/scanner/mirror-report-data.json`. Stop depending on a parallel gap file as the source of truth.
- `public/scanner/app.js` + `public/scanner/styles.css` (local Python UI).
- `web/app.js` + `web/styles.css` (Vercel UI). Same DOM structure so the two pages do not drift.
- `web/dev/check.js` prints band uniques next to category uniques.

Do not start phase 3 until phase 2 fixtures are green. The mirror HTML is generated; edit the builder, not a hand-patched `mirror-mock.html`, except for a one-off local preview.

## 5. New detectors and false-positive strategy

All detectors return hits only. `findings.py` masks, assigns subject, dedupes, and sorts. A hit overlapping a promoted span (same normalized value, or span overlap) keeps the **higher harm**; the lower one is dropped from `findings` but the legacy category count is unchanged.

### Promotion map (no new regex)

Use the post-`categorize()` category, not the raw pipeline type. That is what already routes date-shaped “phones” to `dates` (`DATE_LIKE_RE` in `lib/scanner/report.py`, test `test_dates_misread_as_phones_count_as_dates`).

| Category | Harm | Kind | Confidence | Notes |
|---|---|---|---|---|
| `birthdays` | H2 | `date_of_birth` | medium | Birth cue already required. |
| `bank` | H2 | `iban` | high | Pipeline already checksums IBANs (`regex_stripper.extract_ibans`). |
| `emails` | H4 | `email` | medium | |
| `phones` | H4 if `token.confidence >= 1.0` else H6 | `phone` | high if matcher, low if fallback | Matcher is `phonenumbers.PhoneNumberMatcher` (DE, GB, US) at confidence 1.0; fallback regex is lower (`lib/pipeline/regex_stripper.py`, mirrored in `web/lib/patterns.js`). Date-like values never arrive here. |
| `handles` | H4 | `handle` | medium | |
| `links` | H6 unless reclassified below | `url` | medium | Profile and tokenized subclasses override. |
| `names` | H6 | `name` | low | H4 only for the single span whose cue is `my name is` / `I am` + the span. That one row is kind `self_name`, harm H4, confidence medium. Other names stay H6. |
| `places` | H6 | `place` | low | Precise address/GPS override to H3. |
| `orgs` | H6 | `org` | low | Employer-relation override to H5. |
| `ages` | H6 | `age` | medium | |
| `dates` | H6 | `date` | medium | Never H2. DOB is the `birthdays` row only. |

H6 `name` / fallback `phone` rows exist so the ordered list is honest, but **identity-bridges points ignore them**. The UI corpus disclosure can keep showing the old category chips; it does not need every H6 finding rendered.

Phone confidence must be read off the token at promotion time. `Aggregator` today stores only the original string. Extend `Aggregator.add` to remember the **max confidence** seen for that normalized key (a parallel dict). That is an internal field, not a new public category key. JS `Aggregator` gets the same dict. This does not change `unique` or `examples`.

### Secrets (H1) — `detectors.py`, both prose and fence text

Run on fence slices and on blanked prose. Fence hits set `inCodeBlock: true`. Do not run health, gov-ID, or phone logic inside fences.

| Kind | Pattern (shape, not a new library) | Confidence | Drop when |
|---|---|---|---|
| `private_key` | `-----BEGIN (RSA \|EC \|OPENSSH )?PRIVATE KEY-----` | high | never; the header is enough |
| `aws_access_key` | `\bAKIA[0-9A-Z]{16}\b` | high | — |
| `api_token` | `\bsk-[A-Za-z0-9]{20,}\b`, `\bghp_[A-Za-z0-9]{20,}\b`, `\bgithub_pat_[A-Za-z0-9_]{20,}\b`, Slack `\bxox[baprs]-[A-Za-z0-9-]{10,}` | high | value contains `example`, `xxxx`, `your_`, `redacted`, or is shorter than the floor |
| `jwt` | three dot-separated base64url segments, first starts with `eyJ` | medium | surrounding 40 chars contain `example`, `dummy`, `sample` |

### Subject classification

Window = the same line, up to 80 characters before the span. Apply in `findings.py`, not in the regex module.

| Result | Rule |
|---|---|

### Envelope pass (`lib/scanner/envelope.py`)

Second walk of the zip **names**, plus at most the account member:

- `userJsonPresent`: a member matches `(^|/)user\.json$`.
- If present, `json.loads` that member only. Read string fields among `email`, `email_address`, `phone_number`, `phone`. Mask with the existing email/phone maskers. Emit findings kind `account_email` / `account_phone`, harm **H2**, confidence `confirmed`, subject `account_holder`, source `envelope`. Ignore every other key (`id` included, unless it already matches the email or E.164 phone shape — then it is the same kind, not a new identifier class).
- Do not append these values to `Aggregator`. Chat category tests keep treating `user.json` as skipped.
- `binaryAttachments`: count members whose name contains `.dat` or whose basename starts with `file-`.
- `unreadMembers`: names matching ads / summary / asset index, cap 20.
- Non-zips return the null envelope (`userJsonPresent: null`).

`userJsonSkipped` is true whenever `userJsonPresent` is true. The chat extract path still skips the file; the envelope path is the only reader. Say that in the footnote: “Account file was read only for email and phone, not as chat.”

## 6. Scoring

`exposure_score()` is not replaced. Top-level `score` and `level` stay the corpus-volume index. The UI must not use them as the verdict.

Readouts are computed only from **unique findings** (post-dedupe, pre-cap). Weights:

| Confidence | Multiplier |
|---|---|
| confirmed, high | 1.0 |
| medium | 0.55 |
| low | 0.15 |

| Band | Base points per unique finding |
|---|---|
| H1 | 40 |
| H2 | 0 toward the three meters, except envelope `account_email` / `account_phone` which add into identity bridges at base 30 |
| H3 | 22 |
| H4 account_holder only | 16 |
| H4 third_party or unknown | 0 toward identity bridges (`aboutOthers` still counts) |
| H5, H6 | 0 toward the three meters |

Formula, integer, cap 0–100, half-even round the same way `web/lib/report.js` `roundHalfEven` already matches Python `round` for the legacy score:

```
points = sum(base(kind) * multiplier(confidence))
score  = min(100, round(100 * (1 - exp(-points / SCALE))))
```

Scales: credentials `28`, intimate `36`, identity bridges `24`.

Floors and ceilings (apply after the formula):

- Credentials: if any H1 finding has confidence `confirmed` or `high` and kind is not `jwt`, score = `max(score, 80)`.
- Credentials: `jwt`-only input must stay ≤ 40 even if many JWTs match. Implement by counting JWT points at base 8 instead of 40, and by skipping the floor.
- Intimate: if every H3 finding is `low`, score = `min(score, 35)`. Medium+ removes the ceiling.
- Identity: third-party emails do not move the number. `aboutYou` is the count of H4 (and envelope H2 contacts) with subject `account_holder`. `aboutOthers` is H4 `third_party`.

`readouts.credentials.confidence` is `high` when the floor tripped, else the best H1 confidence, else `low`. Intimate confidence stays `low` when the ceiling is in effect so the meter cannot be read as a diagnosis. Identity confidence is the best confidence among the findings that added points.

Coverage never changes these numbers. It sets `lowerBound` on every readout from `coverage.lowerBound`. A `level: clean` report with `lowerBound: true` is still allowed; the UI copy is “Suspiciously clean — unread bytes mean this is a lower bound,” using the existing `clean` stamp plus the footnote. Do not invent a new level.

## 9. Risks and open questions

**Risks**

- **Fixture blast radius.** Adding keys to `scan()` output forces a `stage1.json` regen in phase 2, including the large zip. Reviewers must look for `unique`/`score` diffs, not only additions. Mitigation: phase 1 does not touch JS; the regen is one commit with the port.
- **Aggregator confidence memory.** Remembering max phone confidence must not change first-seen example strings. Test `test_aggregator_counts_mentions_and_distinct_values` plus a new test that a fallback phone and a matcher phone with the same digits collapse to one unique.
- **Double zip read.** `read_envelope` walks the zip again. Account file only; do not reread `conversations.json`. Cap account member with the existing `MAX_MEMBER_BYTES` mindset — if `user.json` is absurdly large, set `userJsonPresent: true`, emit no contact, add coverage note `userJsonUnreadable: true`.
- **Lexicon harm.** Even masked, the label “Health” on a hit is a disclosure that the export discussed health. That is intended. The masked span must not reveal which condition. Low-confidence hits must not lead the page.
- **False H1 from tutorials.** JWT floor and the example-word reject list are the mitigation. If a real export is full of sample keys, the manual regression in section 7 is the backstop; tighten the denylist rather than lowering the high-confidence floor.
- **Subject errors.** “my” is a blunt cue. Known failure: “my colleague’s email” must be third_party (the negative lookahead in section 5). Add that string as a unit test before shipping copy that says “about you”.
- **Code-fence secrets vs PII.** Scanning fences for secrets will surface keys users pasted into markdown. It will also surface keys inside tutorials. The denylist covers obvious fakes; accept residual medium JWT noise rather than missing PEM headers.
- **Parity drift.** A regex written only in Python will pass pytest and fail the user on Vercel. The detector fixture task is not optional and is not “later”.
- **Name bag still dominates `score`.** That is correct. The risk is a UI that still headlines `level`. Phase 3 copy review is part of the task, not polish.

**Locked decisions (not open)**

- Envelope email/phone are H2 `confirmed`, not mixed into category uniques.
- H2 has no fourth meter. It leads the finding list between credentials and intimate rows.
- Low-confidence H3 does not lead the mirror.
- LLM is out. Cue windows and checksums only.
- Age grammar (“You’re 29”), ISO dates, and NER quality are out.

**Open (need a product call only if you disagree with the default)**

- Default copy for the envelope footnote says the account file was read for email and phone. If that is too alarming, the alternative is to keep `userJsonSkipped: true` and **not** emit contact findings until a later project. This plan emits them. Say so in the PR.
- GitHub profile false positives beyond the denylist (a repo that is a single segment, `github.com/vite`). The denylist is the v1 control; do not add a live HTTP check.
